## 3. Architecture

```
logs/ + deploys.json (+ service_map.yaml)
        │
        ▼
[Hook] redact-sensitive-data  →  writes redacted copy to <output_dir>/work/redacted/
        │
        ▼
[Skill] log-parser (Python)   →  summary.json, clusters.json, timeline.json
        │
        ▼
[Skill] rca-reasoning (LLM + reference/failure-patterns.md)
        │                       reads summaries + targeted line ranges only
        ▼
[Skill] postmortem-writer      →  rca.md, timeline.md, postmortem.md, evidence.json
        │
        ▼
[Hook] evidence-check (Python) →  validates every claim cites existing line IDs
```

**Key principle:** the model never reads full raw logs. Scenarios contain tens of thousands of lines; the agent works from parser summaries and pulls specific line ranges (by `line_id`) as evidence. This keeps context small, cost low and results reproducible.

**Read-only:** the agent never executes remediation, changes config or contacts external systems.

## 5. Data contracts

### 5.1 Log line (JSON lines, one file per service: `logs/<service>.jsonl`)
```json
{
  "line_id": "L004217",
  "ts": "2026-11-20T10:14:03.512Z",
  "service": "order-service",
  "host": "order-2",
  "level": "ERROR",
  "trace_id": "9f2c1a7e",
  "msg": "Timeout acquiring DB connection after 5000ms (pool active=5/5)",
  "http_status": 500,
  "latency_ms": 5012
}
```
- `line_id` is unique across the whole scenario (global counter, zero-padded).
- Levels: `DEBUG`, `INFO`, `WARN`, `ERROR`, `FATAL`.
- Also support plain-text logs in the parser (`<ts> <level> <service> <msg>`); generator outputs JSONL by default.

### 5.2 Deploy / change event (`deploys.json`, array)
```json
{"event_id": "D012", "ts": "2026-11-20T10:02:00Z", "service": "order-service",
 "version": "v2.4.1", "change_type": "config", "details": "db.pool.max_size 50 -> 5"}
```
`change_type`: `deploy` | `config` | `infra` | `feature_flag`.

### 5.3 Service map (`service_map.yaml`)
```yaml
api-gateway: [order-service, inventory-service]
order-service: [payment-service, inventory-service, orders-db]
payment-service: [payment-provider-stub]
inventory-service: [inventory-db]
```

### 5.4 Answer key (`answer.json`) — never shown to the agent during a run
```json
{
  "scenario": "db-pool-exhaustion",
  "seed": 42,
  "root_cause_id": "DB_POOL_EXHAUSTION",
  "root_cause_service": "order-service",
  "trigger_event_id": "D012",
  "fault_start": "2026-11-20T10:02:00Z",
  "key_evidence_line_ids": ["L004101", "L004217", "L004230"],
  "red_herrings": ["L002010"],
  "planted_secrets": [{"line_id": "L003355", "type": "BEARER_TOKEN", "value": "FAKE-tok-..."}]
}
```

### 5.5 Agent evidence output (`evidence.json`) — consumed by evidence-check and run_eval
```json
{
  "status": "ok",
  "hypotheses": [
    {
      "rank": 1,
      "root_cause_id": "DB_POOL_EXHAUSTION",
      "service": "order-service",
      "summary": "Config change D012 reduced DB pool size, causing connection timeouts and a 503 cascade",
      "confidence": "high",
      "evidence_line_ids": ["L004217", "L004230"],
      "related_event_ids": ["D012"]
    }
  ],
  "unverified_claims": []
}
```
- `status`: `ok` | `insufficient_evidence`.
- `confidence`: `high` | `medium` | `low`.
- `root_cause_id` must come from the taxonomy in `failure-patterns.md` (§6.2), or `UNKNOWN`.

## 6. Component specs

### 6.1 Skill: `log-parser`
**Purpose:** deterministic facts about the incident.

| Script | Input | Output | Behaviour |
|---|---|---|---|
| `parse_logs.py` | logs dir, `--min-severity`, `--time-window` | `work/parsed.parquet` or `.jsonl` | Normalise JSONL and plain text; drop below min severity for analysis (keep all for line lookup) |
| `cluster_errors.py` | parsed logs | `clusters.json` | Template errors (Drain3, or a regex fallback that masks numbers/IDs); per cluster: template, count, services, first/last seen, 3 sample line_ids |
| `build_timeline.py` | parsed logs + deploys | `timeline.json`, `summary.json` | Per-minute error rate per service; spike detection (e.g. rate > baseline mean + 3σ); merge deploy events; first error per cluster; top 20 timeline events |
| `get_lines.py` | `--ids` or `--range L004200:L004240` | stdout | Return exact redacted lines so the model can quote evidence |

`SKILL.md` must tell the model: run scripts in order, read only the outputs, use `get_lines.py` for evidence, never `cat` the raw logs.

### 6.2 Skill: `rca-reasoning`
**Purpose:** rank root-cause hypotheses from parser output.

Workflow in `SKILL.md`:
1. Read `summary.json`, `timeline.json`, `clusters.json`, `deploys.json`, `service_map.yaml`.
2. Find the earliest anomaly, not the loudest one. Walk the service map upstream from the symptom.
3. Correlate anomaly start with change events (±15 minutes).
4. Match against patterns in `reference/failure-patterns.md`.
5. Produce up to `max_hypotheses` ranked hypotheses, each with evidence line IDs fetched via `get_lines.py`.
6. Run five-whys on the top hypothesis.
7. If evidence is weak or contradictory, return `status: insufficient_evidence` rather than guessing.
8. Explicitly note red herrings considered and why they were rejected.

**`failure-patterns.md` taxonomy (root_cause_id values):**
`DB_POOL_EXHAUSTION`, `BAD_DEPLOY_CODE_ERROR`, `MEMORY_LEAK`, `CERT_EXPIRY`, `DEPENDENCY_LATENCY`, `DISK_FULL`, `UNKNOWN`.
For each: typical signatures (log messages, metrics shape), usual triggers, distinguishing features vs similar patterns, typical remediation. Write in original wording; do not copy vendor documentation.

### 6.3 Skill: `postmortem-writer`
Produces `rca.md`, `timeline.md` (with a Mermaid timeline or Gantt), `postmortem.md` and `evidence.json`.
Post-mortem sections: Summary, Impact (services, duration, user-facing symptoms), Timeline, Root cause, Five whys, Contributing factors, What went well, Action items (owner placeholder, priority), Evidence appendix.
Two templates: `engineering` (detailed) and `executive` (half a page, no jargon). Blameless tone.

### 6.4 Agent: `incident-analyst.agent.md`
- Orchestrates: redact → log-parser → rca-reasoning → postmortem-writer → evidence-check.
- Accepts parameters from §7.
- Must stop and report clearly if: no logs found, logs unparsable, time window empty, redaction failed. **Never continue on unredacted data.**
- Tools needed: file read/write, shell for Python scripts. No network.
- VERIFY the `.agent.md` frontmatter format with APM docs.

### 6.5 Prompts
| Prompt | Does |
|---|---|
| `/investigate-incident` | Full pipeline, all outputs |
| `/quick-triage` | Redact + parse + top hypothesis only, short answer, plus `symptom` text input |
| `/write-postmortem` | Regenerate post-mortem from existing outputs with chosen `audience` |

### 6.6 Hook: `redact-sensitive-data`
- `redact.py <logs_dir> <out_dir>` writes redacted copies plus `redaction-report.json` (counts per category only, never the values).
- Patterns: email, IPv4/IPv6, bearer tokens, JWT-like strings, `password=`/`secret=`/`api_key=`/`token=` key-values, long hex/base64 secrets, credit-card-like numbers (Luhn check).
- Replacement: `[REDACTED:EMAIL]`, `[REDACTED:IP]`, etc. Preserve `line_id`.
- Redaction mode `strict` (default) or `standard`; cannot be disabled.
- **Enforcement:** VERIFY whether the target runtime supports pre-tool hooks that can block reading the raw log folder. If not, enforce in the agent workflow (agent may only read `work/redacted/`) and state this limitation honestly in the README.

### 6.7 Hook: `evidence-check`
- `check_evidence.py <output_dir>`: validates `evidence.json` against schema; confirms every cited `line_id` exists in the redacted logs; scans `rca.md` and `postmortem.md` for root-cause statements lacking a line ID reference.
- Writes findings to `unverified_claims` and exits non-zero if the top hypothesis has no valid evidence.

## 8. Synthetic data generator

**Fictional app:** ShopSphere, services `api-gateway`, `order-service`, `payment-service`, `inventory-service`, plus stubs `orders-db`, `inventory-db`, `payment-provider-stub`.

`generate_incident.py --scenario <id> --seed <int> [--duration-min 90] [--rps 20] [--out examples/scenarios/<id>]`

Each scenario must include:
- **Background traffic:** INFO request logs with realistic latency distributions; occasional benign WARNs.
- **Noise / red herrings:** at least two unrelated error bursts (e.g. a single 404 spike, a retry warning in another service) that are not the cause.
- **Injected fault:** a trigger (usually a deploy/config event) followed by the causal error pattern and downstream cascade, with plausible delays.
- **Planted fake secrets:** 5–10 per scenario, obviously fake (`FAKE-` prefix, `example.test` emails, private IP ranges) to test redaction.
- **Answer key** as per §5.4, written alongside.
- Fully deterministic for a given seed. Size: ~20k–60k lines per scenario.

| Scenario | Trigger | Causal signature | Downstream effect |
|---|---|---|---|
| `db-pool-exhaustion` | config: pool 50→5 | pool timeout errors in order-service | gateway 503s on checkout |
| `bad-deploy` | deploy vX of inventory-service | NullPointer-style errors on one endpoint | order failures for some SKUs |
| `memory-leak` | deploy of payment-service | rising heap warnings, OOM kills, restarts every ~12 min | intermittent payment timeouts |
| `cert-expiry` | none (time-based) | TLS handshake failures to payment-provider-stub | all payments fail at a sharp time |
| `dependency-latency` | infra event on provider stub | rising upstream latency, retries, circuit breaker opens | slow checkout, retry storms |
| `disk-full` | infra: log level set to DEBUG | write failures, "no space left" errors | inventory-service crash loop |

Also produce **2 hard variants** (e.g. two overlapping changes, or the noisiest service is not the cause) to show honest limitations.

Document all of this in `SYNTHETIC_DATA.md`.

## 9. Evaluation

**Process (semi-automated):**
1. Generate all scenarios with fixed seeds.
2. Run `/investigate-incident` on each scenario **3 times**; save outputs to `runs/<scenario>/run<N>/`.
3. `python examples/evaluation/run_eval.py --scenarios all` reads `evidence.json` + `answer.json` and writes `evidence/scorecard.md` and `scorecard.json`.
4. Record a manual baseline in `manual_baseline.md`: owner times themself doing RCA on 2 scenarios without the tool.

| Metric | Definition |
|---|---|
| Top-1 accuracy | rank-1 `root_cause_id` == answer `root_cause_id` |
| Top-3 accuracy | answer id in any hypothesis |
| Service accuracy | rank-1 `service` == `root_cause_service` |
| Evidence precision | cited ∩ key_evidence ÷ cited (also count cites within ±5 lines of a key line as relevant) |
| Red-herring rate | runs where rank-1 cites a red-herring line |
| Redaction recall | planted secrets absent from redacted logs **and** from all outputs ÷ planted (target 100%) |
| Repeatability | share of runs per scenario agreeing on rank-1 id |
| Time to RCA | wall-clock per run vs manual baseline |
| Unverified claims | count from evidence-check |

Do not tune the reference file or prompts to specific answer keys. Keep scenarios fixed once evaluation begins, and report failures honestly.

## 12. Submission text (already drafted)

**Business Challenge:** During production incidents, engineers spend hours manually searching thousands of log lines across multiple services, matching errors against recent deployments and guessing at the root cause. RCA quality varies depending on who is on call, and post-mortems are often late or incomplete. Logs also contain secrets, IPs and personal data, so engineers can't safely paste them into AI tools. The result is longer outages, repeated incidents and senior engineers tied up in manual investigation.

**Solution Overview:** IncidentLens is an APM package that turns raw logs into an evidence-backed root cause analysis and a ready-to-review post-mortem in minutes. An Incident Analyst agent runs a fixed, auditable workflow through three skills (Log Parser, RCA Reasoning, Post-mortem Writer). Two hooks enforce safety: one masks sensitive data before any model sees the logs; the other flags any conclusion that doesn't cite specific log lines. Ready-made prompts make it usable without writing prompts. Impact is measured against synthetic incidents with known answers.

**Solution Built with Kiro:** Specs for each skill (requirements → design → tasks); steering files encoding data rules, APM structure and coding standards; agent hooks running tests and evaluation on every change; Kiro also used to build the seeded synthetic data generator and evaluation harness. The output is a portable APM package that runs in any compatible agent.
